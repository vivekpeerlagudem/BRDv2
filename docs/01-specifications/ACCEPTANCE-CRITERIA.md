# Acceptance Criteria — Internal Sales CRM, Phase 1

| Item | Value |
|---|---|
| Source | BRD v2.0 §9, §10, §14; Design Foundation (binding) |
| Scope basis | Single-company, single-tenant internal deployment (IDD-01..IDD-16) |
| Companion | [USER-STORIES.md](USER-STORIES.md) — every story lists the FAC IDs that verify it |
| Status | Draft — criteria that depend on a Working Assumption cite the OD and must be re-baselined if the OD is resolved differently |

## 0. Conventions

- `AC-NN` = BRD §14 acceptance criterion NN (numbered 1–18 in the BRD). Quoted verbatim.
- `FAC-<MOD>-NN` = functional acceptance criterion, Given / When / Then. Each FAC is a single testable scenario; negative, error and permission scenarios are separate FACs.
- **Roles in scenarios**: `Admin`, `Manager` (Sales Manager), `SP` (Salesperson), `SP-B` (another Salesperson, not in the Manager's team unless stated), `Buyer` (external recipient), `Viewer` (forwarded viewer), `Signer` (external signer).
- **"Denied"** means: the API returns HTTP 403 `application/problem+json` with a stable `code`, no state changes, and the UI does not offer the action (UI hiding alone never satisfies a permission FAC; ADR-006).
- **"Recorded on the timeline"** means a `timeline_event` exists with the stated type, actor type (user | buyer | system | ai) and timestamp (BR-TIM-004).
- **"Audited"** means an `audit_log` entry exists with actor, action, target, timestamp and, for changes, before/after values (BR-PLT-009).
- **"Within 1 minute"** = NFR-005 notification target (design target < 5 s, ADR-009).
- Release tag `[R1|R2|R3]` follows USER-STORIES.md §2. A FAC is only executed in the release that delivers its story.
- Where a scenario depends on a value the BRD and foundation do not define, the FAC cites the open decision (OD-55..OD-81 in OPEN-DECISIONS.md) and tests its working assumption; the gap is listed in §5 with its OD number.

## 4. Definition of Done — for a requirement (BR / DR)

A requirement is Done for a release when all of the following hold:

1. **Traceability**: the BR (or DR) is linked to its user stories, FACs, business rules, workflows, API endpoints and tests; any OD it depends on is cited and the WA used is unchanged (or the criteria were re-baselined).
2. **Acceptance**: every FAC for the requirement passes in the release's test environment, including negative, permission and error scenarios; automated where feasible (Vitest for domain/API, Playwright for E2E); manual results recorded with evidence.
3. **Permissions**: server-side policy enforced for every role in the ROLE-PERMISSION-MATRIX; denials tested via direct API calls.
4. **Validation and errors**: inputs validated by shared Zod contracts; errors returned as RFC 9457 problem details with stable codes; optimistic concurrency and idempotency applied where ADR-016 requires.
5. **Audit and timeline**: audited actions write `audit_log`; record events write `timeline_event` with actor type; automated changes are labelled and reversible where BR-AUT-008 applies.
6. **Observability**: structured logs with request id and no PII beyond ids; background jobs retried with dead-letter visibility.
7. **Security and privacy**: no secrets in code; buyer-facing endpoints rate-limited; private-email and AI context rules respected; dependency vulnerability scan has no unresolved high/critical findings.
8. **Non-functional**: affected NFR checks in §3 still pass (performance budget for touched screens, accessibility checks for touched UI).
9. **Data**: migrations reviewed and reversible or with a documented roll-forward; seed/configuration content (e.g. starter template, IDD-11) delivered.
10. **Documentation**: user-facing help text and admin configuration notes updated; API OpenAPI spec regenerated; release notes entry written.
11. **Review**: code reviewed by at least one other engineer; Product Owner accepted the demo against the FACs.
